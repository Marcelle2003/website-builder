# Prepare a WordPress website project

Use this for `setup-website`, or as missing preparation during `create`. Its outcome is a locally usable WordPress installation with an active, editable theme, not just an empty directory tree. For preparation alone, stop after the working foundation; do not invent the business or design the whole site. The toolkit's installer copies skill files; the agent performs website preparation separately.

## Establish the project

Infer a sensible project name and location from the request. Clarify only if ambiguity could put work in the wrong place. Keep websites separate from the toolkit checkout. Inspect the destination first. Preserve an existing site's code, database, uploads, editor choices, and conventions; never run a scaffold over it. Switching an existing site from Flatsome, a block theme, or another framework needs an explicit migration scope.

Read the setup record and complete only missing prerequisites from [setup](setup.md). Load the relevant installed WordPress and Tailwind guidance from [supporting skills](supporting-skills.md), then check current official requirements. Use released compatible versions and record authoritative manifests and lockfiles. No Astro frontend, Wagtail service, headless API boundary, or Node production server is needed for the default WordPress architecture.

For a new bespoke site, default to a **hybrid theme**: conventional PHP templates for designed layouts, WordPress blocks for appropriate editable body content, and structured content where it helps editors. This is a classic theme using selected block features, not a third WordPress runtime. Preserve a requested block theme or other existing architecture. Verify the actual template entry points when identifying the theme: a `theme.json` or patterns directory alone does not make a PHP theme a block theme. Use `theme.json` for suitable editor and frontend design settings without assuming full Site Editor ownership of every template. See [theme types](https://developer.wordpress.org/themes/getting-started/what-is-a-theme/) and [theme.json](https://developer.wordpress.org/themes/global-settings-and-styles/introduction-to-theme-json/).

Use the selected local WordPress environment's directory structure. A typical installation contains `wp-content/themes/<theme-slug>/` for templates, theme setup, and compiled assets. Put any site-specific plugin in `wp-content/plugins/<site-slug>-core/` and keep project notes at the actual repository root. Some environments place WordPress outside the theme repository; document the mapping rather than rearranging it. Do not track WordPress core, local database files, credentials, uploads, or unrelated plugins by default. Keep only custom source, necessary configuration examples, and the assets required by the documented deployment path.

## Create a minimal editable theme

1. Prepare the selected local environment with a compatible PHP runtime and MySQL/MariaDB database. Reuse existing services only with the correct site/database isolation; check ports first. Install WordPress in the intended site and configure local URLs and permalinks through its supported flow. Do not reset or destroy a populated environment for verification or as a blanket repair. Inspect failures first; destructive recreation needs a disposable authorized target or a scoped backup/restore plan. A preview using a different database or server must be identified and checked against the intended LAMP host before deployment.
2. Create and activate a minimal theme with valid metadata, PHP fallback templates, standard WordPress hooks, and enqueued assets. Include `wp_head()`, `wp_footer()`, and `wp_body_open()` where applicable so WordPress and plugins can work normally. Keep installation paths and URLs portable. Do not modify core or a vendor theme. If extending an existing parent theme is the authorized choice, use its supported child-theme approach instead.
3. Add a project-local Tailwind build with a documented development/watch command and a production build. Scan the actual PHP and JavaScript sources and include complete class names for supported variants. Content stored only in the database is not automatically scanned: provide deliberate classes/styles for allowed editor content. Enqueue compiled CSS through WordPress; do not depend on the development server or a browser CDN in the deliverable. Coordinate Tailwind tokens with `theme.json` and editor styles, and prevent resets from changing unrelated admin screens.
4. Create a local page with an editable title, introduction/body, and image. Render these through WordPress APIs and the chosen PHP template, including normal block content where intended. Escape output for its context, use WordPress image functions for responsive media, and preserve the distinction between drafts, previews, and public content. Do not claim editing works while showing hardcoded fallback copy.
5. Use core fields and blocks first. Add structured fields or custom blocks when the brief needs them, without forcing a paid field plugin. Content types, taxonomies, and business functionality that should survive a theme change belong in a site plugin. Theme-specific presentation remains in the theme. Explain which items editors can change and which layout/animation changes are made through the AI.
6. Keep JavaScript selective. A setup-only foundation does not need a motion library. When requested creative work needs coordinated animation, prepare the appropriate module/build path and load assets only where used. See the create/improve workflows for motion design and browser verification.

Relevant sources: [WordPress installation](https://developer.wordpress.org/advanced-administration/before-install/howto-install/), [classic theme basics](https://developer.wordpress.org/themes/classic-themes/basics/), [including assets](https://developer.wordpress.org/themes/core-concepts/including-assets/), [Tailwind CLI](https://tailwindcss.com/docs/installation/tailwind-cli), and [source detection](https://tailwindcss.com/docs/detecting-classes-in-source-files).

## Make it usable by its owner

- Supply short, OS-appropriate start/stop instructions and the working website and `/wp-admin/` URLs. Explain any local application's role. Use actual commands and working directories; do not make a Mac-only shell script the sole run path.
- Keep credentials and salts outside tracked files. Provide descriptive configuration examples only where the project uses them. Do not add an `.env` file while assuming WordPress will load it without configuration. Set up the local editor account through the supported flow without committing its password.
- Document how theme assets are built and delivered. A deployable theme must include its compiled assets or have a verified build step in the delivery process. PHP hosting should not require a live asset development server. Describe the intended staging/hosting handoff; preparation does not authorize deployment.
- Create root `AGENTS.md` and a sibling `CLAUDE.md` importing it, following [project instructions](project-instructions.md). Fill them with the actual architecture, skill routing, and verified commands. Merge existing instructions instead of replacing them.
- Create and maintain `WEBSITE_BRIEF.md`, a short run guide, and version records from the conversation and actual setup. The AI writes these; the owner provides creative direction and corrections. Record the editing model and publishing/cache behaviour in plain language.
- Prepare [local feedback handling](feedback.md): preserve existing records, set appropriate ignore rules, and create `SKILL_FEEDBACK.md` only when meaningful evidence exists. A shared inbox remains optional and needs a user-selected location.

## Completion evidence

Run the production asset build and syntax-check custom PHP with the selected compatible runtime. Run any established project lint/standards checks relevant to the foundation. Confirm the correct theme is active and WordPress serves the page without PHP errors. Check a page, a post or archive if provided, local media, and a missing-page response. Asset URLs must work without the watcher running.

Exercise an editor-to-website roundtrip: change a distinctive value and image in disposable local content, save/publish using the normal editor workflow, and verify the exact values on the public page after any documented cache refresh. Confirm a draft is not visible to an unauthenticated visitor. Restore demonstration content where appropriate. Test the editor itself rather than inferring its behaviour solely from a database write.

If browser access is unavailable, verify the available WordPress/HTTP/build checks and clearly state that editor/browser interactions remain untested. Do not report a full end-to-end pass. Missing credentials or prerequisites should leave a resumable record and concrete next step.

Check instructions against actual files and commands, then perform [fresh-chat verification](project-instructions.md#verify-a-fresh-chat) where supported. Record instruction loading separately from website checks; a file existing is not evidence that the agent loaded it.
